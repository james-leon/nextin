# M6 — Écran TV et annonces vocales

Statut : **terminé, en attente de validation** (enchaîné après le M5 à votre demande).

## Ce qui est fait

### L'écran (`/tv`), fidèle à la maquette 05
- **Sans compte**. À la première ouverture, l'écran affiche un **code à 6 chiffres** qui change toutes les 10 minutes. Le personnel le saisit dans le back-office.
- L'écran reçoit alors un **jeton d'appareil**. Le jeton est remis une seule fois et gardé sur l'écran ; seule son empreinte est stockée en base.
- Affichage permanent, toujours sombre :
  - en haut : logo, établissement et agence, heure de l'agence ;
  - **ticket appelé en héros** : numéro en très grand, flèche orange, type et numéro du poste ;
  - en dessous, les **trois appels précédents** ;
  - à droite, la **file de chaque service** (nombre de personnes et attente estimée) ;
  - une carte **QR code d'entrée** de l'agence avec le code court : « Scannez, prenez votre ticket ».
- Seuls les services choisis pour cet écran sont affichés et annoncés.
- Temps réel :
  - les appels arrivent sur le canal public de l'agence (aucun nom) ;
  - après une coupure, l'écran se reconnecte seul, garde le dernier état affiché et montre un indicateur « Hors ligne » ;
  - la configuration est relue chaque minute ;
  - un **écran révoqué revient à l'appairage**.
- Le téléviseur reste allumé si le navigateur le permet (Wake Lock).

### Annonces vocales (§5.6)
- Chaque appel et chaque **rappel** déclenche « Ticket C 47. Présentez-vous au cabinet 3. ». L'état affiché au démarrage n'est jamais annoncé.
- Fonctionnement :
  - une annonce à la fois, précédée d'un **carillon** synthétisé (aucun fichier à charger) ;
  - français, anglais, ou les deux à la suite ;
  - volume, répétitions (1 à 3) et **plage de silence** : l'affichage continue, sans le son.
- **Voix enregistrées** : un fichier MP3 par segment (mots, lettres A–Z, nombres 1–999) et par langue, généré avec ElevenLabs par `pnpm voices:generate` et stocké dans le bucket public Supabase `voices`. Un `manifest.json` liste les segments disponibles ; l'écran les met en cache.
- **Repli** : s'il manque un segment (voix pas encore générées, libellé de poste personnalisé, numéro au-delà de 999), la phrase est dite par la **synthèse vocale du navigateur**. C'est le cas aujourd'hui tant que les voix ne sont pas générées.
- Bouton « Activer le son » : les navigateurs exigent un premier geste. Certains boîtiers l'autorisent d'emblée, et le bouton indique alors « Son activé ».
- Logique partagée et testée dans `@nextin/shared/announcements` : séquence des segments, texte de repli, plages de silence (y compris celles qui passent minuit).

### Back-office : Agence → « Écrans de la salle d'attente »
- Adresse à ouvrir sur le téléviseur (bouton copier).
- **Appairer** : code, nom de l'écran, services affichés (tous par défaut). Un code inconnu ou expiré est refusé.
- Liste des écrans : « En ligne » ou « Vu le … », nombre de services.
- **Modifier** (nom, services) ou **révoquer** (avec confirmation) un écran.
- **Annonces vocales** : langues, volume, répétitions, carillon, plage de silence.
- Réservé à l'org_admin et au responsable de l'agence. Les autres membres du personnel ont une consultation seule.

### Base de données (`supabase/migrations/20261101090000_m6_displays.sql`)
- Tables :
  - `displays` : en attente, l'écran n'appartient encore à aucun établissement ; empreinte du jeton, dernière présence, version ;
  - `display_services` ;
  - `announcement_settings`.
- RPC du serveur (service role uniquement) : `tv_create_pairing` (limité à 20 codes par tranche de 10 min et par IP), `tv_poll_pairing` (jeton remis une fois), `tv_session`.
- RPC du personnel : `pair_display` (droits de gestion de l'agence, limité contre la recherche de codes au hasard), `update_display`, `revoke_display`. Toutes sont journalisées dans l'audit.
- Routes : `POST /api/tv/pair`, `POST /api/tv/pair/poll`, `GET /api/tv/session` (jeton en Bearer ; l'URL du QR code est construite depuis `APP_URL`).
- RLS : les colonnes des empreintes de jeton ne sont **jamais lisibles**, même par le personnel. Isolation entre établissements testée.
- Écart avec le plan : le bucket `voices` est créé par le script de génération, pas par une migration (le stockage n'existe pas sur la base locale de test).

### Divers
- Le bouton « gris » utilise désormais `text-accent-on-tint` : contraste AA même posé sur le fond groupé.
- `ListSection checkboxGroupLabel` : rôle ARIA `group` pour les choix multiples (formulaires Écrans et Guichets).

## Correctif après validation : derniers appels (`20261102090000_m6_recent_calls.sql`)
- **Problème** : `branch_board.calls` ne renvoyait que les tickets `called` / `serving`. Avec un seul praticien, les trois tuiles « derniers appels » restaient donc vides.
- **Correction (nouvelle migration, l'ancienne est inchangée)** :
  - `calls` contient les appels du jour, y compris terminés (`served`, `no_show`, `transferred`), triés par dernier appel, 12 au plus ;
  - un appel terminé reste 30 minutes ; un appel en cours reste affiché quelle que soit son ancienneté.
- Le héros reste le dernier patient alerté (`called`), sinon l'appel le plus récent (`lib/tv/calls.ts`).
- Sans appel précédent, un tiret discret remplace les trois rectangles vides.
- Confidentialité inchangée : numéro, service et poste uniquement (vérifié par pgTAP).
- Les autres lecteurs du tableau (appels en cours de l'accueil, « En cours » de la page Mon ticket) filtrent les appels en cours avec `isActiveCall`.
- **Course corrigée au passage** : une relecture du tableau partie avant un appel pouvait revenir après sa diffusion temps réel et l'écraser. La page Mon ticket restait alors sur « 2 devant vous » (test client instable). `subscribeBoard` (`lib/client/board-feed.ts`) ignore désormais une relecture si une diffusion est arrivée entre-temps.
- Tests :
  - pgTAP `m6_recent_calls.test.sql` (10) : un cabinet appelle, termine trois tickets (dont un absent) et alerte le quatrième ; les trois précédents restent au tableau. Sont aussi vérifiés la fenêtre de 30 minutes, la limite de 12, les autres jours et les champs exposés.
  - Vitest : `tvCalls`, `createBoardFeed`.
  - Playwright `tv.spec.ts` : tiret avant le premier appel précédent, puis tuiles C-003, C-002, C-001 avec un seul cabinet.
- À appliquer sur la base distante : `pnpm db:push`.

Parcours Playwright du M6 :
1. Code affiché sur l'écran, saisie d'un code erroné puis du bon.
2. L'écran passe seul à l'affichage, et le back-office le montre « En ligne ».
3. Appel : ticket en héros et poste affichés, **annonce prononcée** « Ticket C 1. Présentez-vous au cabinet 3. ».
4. Rappel annoncé à nouveau ; l'appel suivant fait passer l'ancien dans la rangée du bas.
5. **Révocation** : l'écran revient à l'appairage.

Les réglages d'annonce sont aussi testés, avec le contrôle d'accessibilité.

## Montrer aux cliniques pilotes
1. Sur le téléviseur ou un boîtier Android, ouvrir `<APP_URL>/tv` et passer en plein écran (F11, ou le mode kiosque du boîtier).
2. Dans le back-office : DOUALA CLINIC → Akwa → **Écrans de la salle d'attente**. Saisir le code affiché sur le téléviseur.
3. Toucher une fois « Activer le son » sur le téléviseur.
4. Depuis `/desk`, ouvrir le cabinet 1 et appuyer sur « Alerter le suivant » : le numéro s'affiche et s'annonce.

## À faire de votre côté
- Appliquer la migration M6 sur la base distante : `pnpm db:push`.
- **Voix ElevenLabs**, pour une voix naturelle plutôt que la synthèse du navigateur :
  1. Renseigner dans `apps/web/.env.local` : `ELEVENLABS_API_KEY` (elevenlabs.io → Profile → API Keys) et `ELEVENLABS_VOICE_ID_FR` / `ELEVENLABS_VOICE_ID_EN` (Voice Library). `ELEVENLABS_MODEL_ID` est facultatif ; par défaut, `eleven_multilingual_v2`.
  2. Lancer `pnpm voices:generate`. Cela représente environ 2 060 segments par langue ; le script reprend là où il s'est arrêté.
  3. Pour estimer d'abord le volume : `pnpm voices:generate --dry-run`.
