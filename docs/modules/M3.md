# M3 — Moteur de file d'attente, estimation de l'attente et temps réel

Statut : **terminé, en attente de validation.**

Ce module ne contient pas d'écran : les pages client arrivent au M4, le poste de l'agent au M5, l'écran TV au M6. Il livre le moteur sur lequel ces écrans s'appuieront, l'API de prise de ticket et la diffusion en temps réel.

## Ce qui est fait

### Base de données (`supabase/migrations/20261029090000_m3_queue_engine.sql`)
- Tables : `daily_sequences` (numérotation par service et par jour local de l'agence), `tickets`, `ticket_events` (journal du parcours), `service_time_stats` (durées mesurées, par service et par poste), `client_ops` (idempotence des commandes des postes).
- **États du ticket et appel en deux temps** :
  `waiting` → « Alerter le suivant » → `called` → « Admettre » → `serving` → `served`.
  Depuis `called`, le patient peut aussi être rappelé (`recall`) ou déclaré absent (`no_show`).
  Les états `cancelled` et `transferred` complètent la liste.
  Le **chrono démarre à l'admission** (`serving_started_at`) : la durée mesurée court de l'admission à la fin, jamais depuis l'alerte.
- Un poste n'a **jamais plus d'un ticket alerté ou admis**. Un index unique le garantit même en concurrence.
  `call_next` est refusé (`counter_busy`) tant que le patient alerté n'est ni admis, ni rappelé, ni déclaré absent.
  « Terminer et alerter le suivant » (`p_finish_current`) termine d'abord le patient admis.
- **Ordre de passage** : poste attitré d'abord, puis priorité (rendez-vous, grossesse, personne âgée, handicap…), puis ancienneté et numéro.
  `call_next` verrouille les lignes avec `FOR UPDATE SKIP LOCKED` : deux postes qui appellent en même temps n'alertent jamais le même ticket.
- **Prise de ticket client** : `take_ticket`, appelable seulement avec la clé service role, donc par le serveur de l'application. Elle vérifie, dans l'ordre :
  - le QR code ou le code court de l'agence (insensible à la casse) ;
  - les horaires et les fermetures exceptionnelles ;
  - le service actif et son quota du jour ;
  - la priorité autorisée et le ticket à distance activé ;
  - un seul ticket actif par client et par agence. Si le client en a déjà un, on lui rend le lien de ce ticket.
- **Limitation** : `throttle_ticket_request` est appelée dans une transaction à part, si bien que les tentatives refusées comptent aussi. Plafonds : 10 demandes par heure et par client, 60 par tranche de 10 min et par IP hachée.
- **Commandes du personnel** :
  - `reception_create_ticket` : ticket d'accueil, sans client rattaché ;
  - `open_counter`, `pause_counter`, `close_counter` : en pause ou à la fermeture, les patients attitrés repassent dans la file commune ;
  - `call_next`, `admit_ticket`, `recall_ticket`, `mark_no_show`, `finish_ticket`, `cancel_ticket`.

  Ces commandes acceptent un `p_client_op_id` : rejouée après une coupure réseau, une commande renvoie le même résultat sans agir deux fois. Les droits sont revérifiés au rejeu.
- **Autres commandes de l'accueil** :
  - `transfer_ticket` (réorientation) : nouveau numéro dans le service cible, mêmes priorité et ancienneté, et le lien du client suit le nouveau ticket ;
  - `set_ticket_priority` (journalisé dans l'audit) ;
  - `move_back_ticket` (recul de 1 à 50 places, sans renuméroter).
- **Surface publique, sans aucune donnée personnelle** :
  - `resolve_entry(code)` : agence, services ouverts, attente estimée ;
  - `get_branch_board(agence)` : codes en attente, appels en cours et postes ;
  - `get_ticket(jeton)`, `cancel_my_ticket(jeton)` et `rate_ticket(jeton, note)` : note de 1 à 5, une seule fois, après le passage.
- Erreurs métier : le message est le code (`counter_busy`, `branch_closed`…) et le SQLSTATE vaut `P0404`, `P0409`, `P0410`, `P0422` ou `P0429`. Chaque code a un message FR/EN dans le dictionnaire `errors`.
- RLS : un client ne lit que ses tickets ; le personnel lit les tickets de son agence ; le journal et les statistiques sont réservés au personnel. Aucune écriture directe : tout passe par les RPC.
- **Tâches planifiées (pg_cron)** :
  - `expire_stale_tickets` à 00 h 05 : clôture les tickets de la veille ;
  - `purge_personal_data` à 02 h 35, après `data_retention_days` : efface le jeton du lien, le compte anonyme rattaché et le commentaire libre. La note anonyme reste pour les statistiques ;
  - la purge des comptes anonymes inactifs épargne désormais ceux qui suivent un ticket actif.

### Estimation de l'attente (`packages/shared/src/queue/estimate.ts`, miroir SQL)
- Les postes travaillent en parallèle : le premier libre prend le suivant (simulation gloutonne). Le temps restant du patient en cours est pris en compte.
- Durée retenue :
  - durée par défaut saisie par la direction jusqu'à 10 mesures ;
  - mélange progressif sur les 20 mesures suivantes ;
  - au-delà, moyenne mobile exponentielle (α = 0,2).

  On utilise la durée du poste quand il a assez de mesures, sinon celle du service.
- Mesures ignorées : moins de 20 s, ou plus de 4 fois la moyenne une fois qu'on dispose de 10 mesures.
- **Parité TypeScript / SQL** : `estimate.fixtures.json` (9 cas) est vérifié par Vitest. Le même fichier sert de référence aux appels SQL de `m3_queue.test.sql`, et Vitest échoue si un cas manque côté SQL.

### Temps réel (Realtime Broadcast, `packages/shared/src/queue/realtime.ts`)
- Des déclencheurs SQL diffusent à chaque changement d'un ticket ou d'un poste :
  - `branch:<agence>:board` (public) : le tableau de l'agence, pour l'écran TV et la page client ;
  - `ticket:<jeton>` (public, nom secret) : la vue du ticket pour son détenteur ;
  - `staff:branch:<agence>` (privé) : réservé au personnel de l'agence par une politique RLS sur `realtime.messages`.
- Aucun nom n'est diffusé : seulement des codes (`C-047`), des postes et des durées.

### Application
- `POST /api/tickets` (`app/api/tickets/route.ts`, logique dans `lib/queue/take-ticket.ts`).
  - Étapes : JSON uniquement (protection anti-CSRF), validation Zod (`takeTicketSchema`), session (cookie de la PWA ou jeton Bearer pour l'app native du M11), limitation, captcha Turnstile vérifié côté serveur, puis `take_ticket` avec la clé service role.
  - Réponse en cas de succès : 201 `{ ticket: { publicToken, displayCode, url } }`, avec un `url` construit depuis `APP_URL`.
  - Réponse si le client a déjà un ticket : 409 `active_ticket_exists` avec le lien de ce ticket.
- `mapDbError` reprend les codes métier de la file. `23503` devient `in_use` : supprimer un service qui a un historique de tickets est refusé avec un message clair invitant à le désactiver.
- Types de la base régénérés (`pnpm db:types`).

## À faire de votre côté
- Appliquer la migration M3 sur la base distante : `pnpm db:push`.
- Ajouter `IP_HASH_SALT` dans l'environnement de production (Vercel → Settings → Environment Variables) : une chaîne aléatoire longue, par exemple `openssl rand -hex 32`. Avec le captcha actif, la route de prise de ticket refuse de fonctionner sans elle.
- Vérifier sur le projet distant que Realtime est actif (Dashboard → Realtime). Les canaux privés du personnel reposent sur la politique RLS créée par la migration.
